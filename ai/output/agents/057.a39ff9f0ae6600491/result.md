Report: quota-window-reset / gray-overlay research (no code changes).

**Window boundaries — DB/API-side already, not frontend.** `build_windows()` in `src/ai_usage/graph.py:226` groups `MetricSampleRecord`s by the tuple `(reset_at, window_seconds)` (both provider-reported, columns in `src/ai_usage/orm.py:59`). Each distinct tuple becomes one `GraphWindow`. So a real provider-side rollover (new `reset_at`) already splits into a new window automatically — the gap the user describes only exists for **mid-window quota bumps that don't change `reset_at`/`window_seconds`** (their copilot example: same session/window, but max jumps 5000→7000 without a new reset timestamp).

**Gray "100%-blocked" overlay** — `build_windows()` line 245-248 sets `exhausted_from` to the timestamp of the *first* sample in that window group with `percentage >= 100`, and never re-checks later samples in the same group. Frontend renders the gray band in `frontend/src/chart.ts:535-545`: a piecewise area from `exhausted_from` to `window.end` at y=0→100, opacity 0.3, unconditional on later percentage. So once any sample in a window hits ≥100%, the overlay persists to `window.end` regardless of subsequent drops — exactly the stale-block bug.

**Per-sample data**: percentage/current/maximum are per-sample (`GraphPoint`/`MetricSampleRecord`), not aggregated — a threshold-drop detector (frontend or backend) has full per-point resolution to work with.

**No existing reset/rollover/drop-tolerance logic found.** Grep across `graph.py`/`models.py`/`orm.py` for "reset"/"rollover"/"refresh" only turns up the existing `reset_at` field and `with_window_reset_zeros()` (synthetic 0% point at `window.end` for past windows — cosmetic, not detection). No `<2%` caching-noise tolerance constant exists anywhere in the Python graph code or `chart.ts`; the user's "ignore <2% drops" is either tribal knowledge not yet encoded, or lives in provider-parsing code not covered by this search (not checked).

**Minimal model changes needed**, in order of where reset detection should live:
- **DB-side (recommended per user's instinct)**: `build_windows()` needs a synthetic re-split — when consecutive samples in the same `(reset_at, window_seconds)` group show percentage dropping by more than a tolerance (e.g. >2%) *and it's not explained by a `maximum` decrease alone*, cut the group into two `GraphWindow`s at that sample. This reuses the existing grouping mechanism (just add a second split predicate) rather than requiring new persisted fields.
- `GraphWindow.exhausted_from` semantics need fixing regardless: it should stop applying once the *current* window segment's samples are back under 100%, i.e. it must be recomputed per split sub-window, not just first-ever-≥100 in the whole DB-grouped bucket.
- API contract (`GraphWindow` in `models.py`/`types.ts`) needs no new fields if splitting happens before window construction — same shape, just more window instances with correct `start`/`end`/`exhausted_from`/`maximum_percentage` per segment.
- If drop detection instead stays frontend-only, `GraphSeries.points` already has everything needed, but `windows[]` (used for the gray overlay, projections, tooltip window-stats) would need to be independently re-split client-side too, duplicating the split logic in both languages — the DB-side split is simpler and single-sourced.
