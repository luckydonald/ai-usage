# Why `CLAUDE_CONFIG_DIR=/home/user/.claude claude` re-triggers first-time setup

## Symptom

Explicitly setting `CLAUDE_CONFIG_DIR` to the default config directory path (`/home/user/.claude`)
was expected to be a no-op, since that is already the default location Claude Code uses when the
variable is unset. Instead, it caused Claude Code to behave as if run for the first time
(re-onboarding, `Config install method: unknown` instead of `native`).

## Root cause

Claude Code's main state/config file (`.claude.json` — holds install method, credentials
references, project registry, usage counters, etc.) does **not** live inside the config directory.
By default it lives as a **sibling** of it:

```
/home/user/.claude.json      <- main state file (parent dir of config dir)
/home/user/.claude/          <- config dir (settings.json, plugins, skills, credentials, ...)
```

`CLAUDE_CONFIG_DIR` only relocates the config directory itself. But the code that locates
`.claude.json` derives its path from the config dir setting too — and it looks for it **nested
inside** the config dir, not beside the config dir's default parent:

```
$CLAUDE_CONFIG_DIR/.claude.json
```

So:

- **Unset** (default): config dir resolves to `~/.claude` → its "parent" for `.claude.json`
  purposes is `$HOME` → reads `/home/user/.claude.json`. Real file, real data. Works.
- **Set to `/home/user/.claude`** (same literal path as the default): the code now looks for
  `/home/user/.claude/.claude.json` (nested one level deeper than the default resolution). That
  file does not exist yet → Claude Code treats it as a fresh install: no known install method
  (`unknown`), no known projects/usage history, onboarding flow triggers again.

This was confirmed with `strace -f -e trace=openat` on `claude doctor` (a non-interactive,
read-only diagnostic command), comparing file opens with and without the env var set to the
identical path:

```
# default (no env var) — reads/writes:
/home/user/.claude.json
/home/user/.claude.json.tmp.<pid>.<hash>
/home/user/.claude/backups/.claude.json.backup.<timestamp>

# CLAUDE_CONFIG_DIR=/home/user/.claude — reads/writes instead:
/home/user/.claude/.claude.json
/home/user/.claude/.claude.json.tmp.<pid>.<hash>
```

`doctor` output confirmed the effect directly:

```
# default
Config install method: native

# CLAUDE_CONFIG_DIR=/home/user/.claude
Config install method: unknown
1 warning found
- Running native installation but config install method is 'unknown'
  Fix: Run claude install to update configuration
```

## Takeaway

`CLAUDE_CONFIG_DIR` is **not** a drop-in equivalent for "the directory Claude Code would use by
default" — setting it, even to a value that matches the default, changes where the top-level
`.claude.json` state file is expected (nested under the dir, instead of beside it). Setting the
env var and leaving it unset are not equivalent operations, even for the "same" path.

## Practical implications

- Don't set `CLAUDE_CONFIG_DIR` unless you actually want an alternate config tree — leaving it
  unset is not equivalent to setting it to the default path.
- If you must set it (e.g. via a wrapper/alias/`direnv` for per-project isolation), be aware the
  new tree starts empty: no existing credentials, project registry, or usage history carries over
  unless you seed `$CLAUDE_CONFIG_DIR/.claude.json` yourself (e.g. by copying
  `~/.claude.json` → `~/.claude/.claude.json` for this specific case).
- This was diagnosed with `strace`, not by reading source — the exact code path (which function
  derives the `.claude.json` location from `CLAUDE_CONFIG_DIR`) was not inspected directly.
